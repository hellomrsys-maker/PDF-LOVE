# PDF Love test report

Generated 2026-08-01 15:50 UTC from commit `8478318`.

Regenerated by `python scripts/build-report.py` from what the suites measured. Anything a suite did not produce appears as "not run", never as a pass.

## Bugs found

15 defects, 14 fixed, 1 open.

### BUG-001 — Three server-assisted tools advertised "runs on-device"  
**FIXED**

PDF to PowerPoint, PDF to Excel and PDF to PDF/A sat in the always-visible Convert row, whose cards are labelled on-device by section. The privacy claim on the card was false, and the published count was wrong: 94 tools run on-device, not 97.

*How to see it:* Open the app with no backend configured and read the badge on PDF to Excel.

### BUG-002 — Passport & ID Photo Maker crashed on every use  
**FIXED**

`viewH` was declared inside setupCropper but read by the Create handler, so every click threw ReferenceError and no photo was ever produced.

*How to see it:* Open the tool, load a photo, click Create.

### BUG-003 — pdf.js detached the caller's file buffer  
**FIXED**

getDocument transfers the buffer to its worker, which leaves the caller holding a zero-length ArrayBuffer. Any tool that read a file once and then passed the same bytes to pdf-lib reported "Could not read this PDF" on a perfectly valid file. Bookmarks/TOC failed on every document; Split by Bookmark failed on every document that had bookmarks.

*How to see it:* Load fixtures/text.pdf into Bookmarks / TOC.

### BUG-004 — Extract Images found nothing in files full of images  
**FIXED**

It asked pdf.js for image objects through page.objs, which is only populated after a page has been rendered. It now reads the XObject dictionaries directly, and returns original JPEG bytes rather than re-encoding every photo to PNG.

*How to see it:* Run it on fixtures/scanned.pdf, which contains 2 embedded images.

### BUG-005 — Repair PDF could not repair anything  
**FIXED**

It only re-saved files that already parsed — the opposite of its purpose. It now falls back to the bundled qpdf engine, which rebuilds a damaged cross-reference table by scanning for objects.

*How to see it:* fixtures/corrupt.pdf (broken xref) now comes back with all 3 pages; fixtures/truncated.pdf is genuinely unrecoverable and now says so.

### BUG-006 — Images to Slideshow Video crashed on its first frame  
**FIXED**

The first requestAnimationFrame timestamp can predate the t0 sampled immediately before it, making floor(t/secs) return -1 and bitmaps[-1] undefined.

*How to see it:* Add two photos and click Create.

### BUG-007 — Trim Video produced a zero-byte file and called it done  
**FIXED**

Two faults. MediaRecorder was attached to a video element that had not yet presented a frame, so Chromium raised EncodingError on every container it offers; and isTypeSupported reports video/mp4 as supported while its muxer cannot encode an element capture. The tool now waits for a real frame and falls back through containers until one actually emits data — and refuses to hand over an empty file.

*How to see it:* Trim fixtures/clip.webm; it now yields a ~77 KB clip.

### BUG-008 — Wrong password reported as "engine failed to load: undefined"  
**FIXED**

Emscripten throws an ExitStatus object with no .message. Exit codes are now mapped to real sentences, and the cached WASM module is dropped after a failure so an aborted runtime cannot poison later attempts.

*How to see it:* Enter a wrong password in Unlock PDF.

### BUG-009 — Fourteen of twenty file handlers failed silently  
**FIXED**

Async onFiles handlers had no error handling, so an unreadable file became an unhandled rejection and the panel simply sat there — indistinguishable from a tool that does nothing. This is the most likely explanation for "most features don't work": they reported nothing when they failed.

*How to see it:* buildDropzone now routes every entry point through a guard that always reports.

### BUG-010 — The canonical URL pointed at a domain that did not exist  
**FIXED**

Every page declared a canonical host with no DNS record, so the markup told crawlers the authoritative copy of each page was unreachable. The site now lives at pdflove.co.in, which resolves.

*How to see it:* python scripts/check-canonical.py

### BUG-011 — CI stopped syntax-checking the app, and said nothing  
**FIXED**

The frontend-syntax job pulled the app out of an inline <script> in index.html. That script moved to frontend/app.js, so the match returned null and the job threw a TypeError on every push. app.js — the whole product — had no syntax check at all, "every tool card resolves to a real function" never ran, and the duplicate-name check scanned index.html, found zero tool names, and passed vacuously. Each check now reads app.js and asserts it found something, so a pattern matching nothing fails loudly instead of reporting success.

*How to see it:* The three steps at the top of .github/workflows/validate.yml.

### BUG-012 — The redaction and OCR checks could never have passed honestly  
**FIXED**

Both read a PDF's text layer. Without pdfminer.six — which CI never installed — they fell back to decoding the raw file as latin-1. A PDF's content streams are compressed and its strings may be hex-encoded, so that search finds nothing whether or not the secret is there: a redaction test that cannot fail. The same fallback made a working OCR tool look broken by matching the phrase against 103,381 bytes of compressed binary. A second bug — an except clause that was a sibling rather than a parent of the one that raised — let a pikepdf error escape as a bare "PdfError", which read like a product crash. The fallback is gone; the checkers now fail loudly when the dependency is absent.

*How to see it:* node scripts/functional-suite.js --only "Search & Redact"

### BUG-013 — The privacy policy overstated how many tools run on-device  
**FIXED**

The site claimed 97 of 104 tools were on-device. The real number is 94: three server-assisted converters sit in the always-visible Convert row. The wrong figure was in the privacy policy, the terms, the About and download pages, and the FAQPage JSON-LD that feeds Google's rich results. check-tool-counts.js existed to prevent exactly this and missed it three ways — it never scanned those files, its pattern required "N of M" where the text said "N of the M", and it understood only digits, so "Ninety-seven of them" was invisible.

*How to see it:* node scripts/check-tool-counts.js

### BUG-014 — 149 tool pages shipped with no test of any kind  
**FIXED**

The tool pages were made page-native, rendering into #panel-body-mount. functional-suite.js only ever loads index.html and scopes every selector to #panel-body, so it could pass in full while every one of those pages was broken — and they are where search traffic lands.

*How to see it:* node scripts/page-native-test.js

### BUG-015 — Nine of eleven chained-tool suggestions are dead config  
**OPEN**

SUGGESTED_NEXT names a follow-up for eleven tools, but only Make PDF Smaller and Scan Document call offerChain, which is what renders the "Also want to ..." button. For the other nine — including Merge PDF, Split PDF, Images to PDF and Sign PDF — the entry exists and nothing ever shows it. Not a visible fault, but a designed feature that silently does not run.

*How to see it:* Compare the offerChain call sites in frontend/app.js against the SUGGESTED_NEXT keys.

## Capacity

Memory does **not** track a document's size in bytes. It tracks the **page count**, because the output document holds a page-tree entry for every page until the writer finishes.

| Source | Input | Pages | Peak RSS | KB/page |
|---|---|---|---|---|
| few | 2775 MB | 240 | 43 MB | 184.9 |
| many | 5227 MB | 12000 | 216 MB | 18.4 |

Twice the bytes, fifty times the pages, five times the memory.

| Copies | Pages | Input | Peak RSS | KB/page |
|---|---|---|---|---|
| 1 | 3000 | 1307 MB | 68 MB | 23.1 |
| 4 | 12000 | 5227 MB | 216 MB | 18.4 |
| 16 | 48000 | 20907 MB | 808 MB | 17.2 |
| 40 | 120000 | 52267 MB | 1995 MB | 17.0 |

**Batching the input does not help.** Cascading a 48,000-page merge through 8 intermediates lowered the intermediate peak to 116 MB, but the final pass still cost 804 MB — identical to merging directly, and twice as slow.

**Capping pages per output file does.**

| 48,000-page merge | Parts | Peak RSS | Time |
|---|---|---|---|
| one file | 1 | 812 MB | 33.7s |
| 6,000 per part | 8 | 124 MB | 17.8s |
| 3,000 per part | 16 | 75 MB | 21.1s |

Same 4.93 GB of output either way. `merge_paths(max_pages_per_part=N)`, or pass `memory_budget_mb` and let the engine choose.

What this means in practice: 20,000 pages costs about 500 MB in a single file, so a desktop handles it directly. A 100 GB job is 76,000+ pages and about 1.3 GB in one file — fine on a computer, too much for a phone's per-app ceiling, which is what the part cap is for.
